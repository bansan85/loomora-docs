# ADR 0017: The Web family has a WebAssembly path (current Emscripten) and a JavaScript path (Emscripten 1.39.20 fastcomp); Internet Explorer up to 9 is dropped

- **Status**: accepted
- **Date**: 2026-11-15
- **Spike / requirement**: S5 (T070) / FR-017, FR-022, research R8, spec Clarifications of 2026-11-15 (PoC validation scope)

## Context

The Web family must serve browsers of the Nov-2011 generation with the Legacy UI (research R8) from the same C++11 backend, compiled by Emscripten behind the C API of `loomora.h` (ADR 0001). R8 planned: a WebAssembly path with the current Emscripten, and a JavaScript path built first with the current Emscripten (`-sWASM=0 -sLEGACY_VM_SUPPORT=1`) and rebuilt with Emscripten 1.39.20 fastcomp only if the first failed on the old browsers. The first wording of spike S5 named IE 9, Firefox 8, Chrome 15, Safari 5.1 and Opera 11.5. What was measured on 2026-11-15 (WSL Ubuntu 24.04, node, then a Windows 2000 VM):

- **Current Emscripten 7.0.0** (clang 24) still **accepts** `-sWASM=0 -sLEGACY_VM_SUPPORT=1` (only the warning "WASM=0 is deprecated", emscripten issue 27608) and builds a working JavaScript-only `loomora.js` (61,551 bytes, no `.wasm`) that passes the 43 checks of `tools/trials/web-node/s5-node-driver.js` and the self-test with the `WebAssembly` global deleted. But the output is **ECMAScript 2021**: acorn parses it only as `ecmaVersion 2021` (arrow functions, async functions, optional chaining, `globalThis`, default parameters; its first token is a syntax error for an older engine). `LEGACY_VM_SUPPORT` only lowers the `MIN_*_VERSION` settings and does not change the syntax. Evidence: `validation/evidence/web-s5/linux-ubuntu-24.04-x86_64/emscripten-7.0.0-js.txt`. This is a reading of the syntax, not a browser run.
- **Emscripten 1.39.20 fastcomp** (`-sWASM=0 -sLEGACY_VM_SUPPORT=1 --memory-init-file 0`) builds true asm.js: `loomora.js` is 91,529 bytes with the memory image embedded, the glue **parses as ECMAScript 3**, and it passes the 43 checks and the self-test without `WebAssembly`. The upstream (wasm2js) backend of the same 1.39.20 release also builds an ES3 glue (86,727 bytes + 2,018 bytes `.mem`) and passes the same checks under node; it was not run in a browser. Evidence: `emscripten-1.39.20-fastcomp-js.txt`, `emscripten-1.39.20-js.txt` (web-s5) and `emscripten-1.39.20-fastcomp-es3.txt` (web-es3).
- **No typed-array-free build exists**, so Internet Explorer 6 to 9 cannot run any build that was found. Evidence: `validation/evidence/web-es3/linux-ubuntu-24.04-x86_64/`.
  - Fastcomp 1.39.20: `USE_TYPED_ARRAYS` is no longer a setting (`emcc: Attempt to set a non-existent setting`, removed in 1.30.6) and `ASM_JS=0` is refused, so the output is asm.js on `HEAP8` / `HEAP32` / `HEAPF64` views. With `ArrayBuffer`, `DataView` and the eight typed array constructors deleted, `loomora.js` stops at load (21 constructor calls).
  - **Emscripten 1.29.12**, the last release with the old compiler core (stock clang 3.3, Python 2.7.18 built from source, three local patches listed in the log), still has the plain-array mode `USE_TYPED_ARRAYS=0`. A C hello world builds and runs with every typed array global deleted, but a C++11 program using `std::string` makes the compiler core crash (`Internal compiler error in src/compiler.js ... Cannot read property '0' of undefined`, after "64 bit XOR - precision limit may be hit"): 64-bit integer arithmetic of libc++ is not implemented without typed arrays. The Loomora backend fails the same way, with or without `-O1 --llvm-lto 1`. Its glue also uses ES5 library functions (`forEach`, `filter`, `Function.prototype.bind`, `Object.defineProperties`).
  - Releases from 1.30.0 on: not run, read from the source of the tag 1.30.5: `emcc` asserts "fastcomp assumes ta2" and "ASM_JS must be enabled in fastcomp", and `emscripten.py` prints "Non-fastcomp compiler is no longer available". Releases before 1.29.12 were not tried.
- **Lowest testable browser**: Firefox 10.0 (build ID 20120129021758) on Windows 2000 build 2195, in the VirtualBox VM "Windows 2000". It has typed arrays and ES5, no WebAssembly. It ran the fastcomp build: `core` is `cpp-js`, the server log shows `loomora.js` and never `loomora.wasm`, "Bonjour Coucou", then "Bonjour Marie" typed; 15 vectors run, 14 pass (`control_characters` differs only by its line feed, which an HTML text field removes in every browser). Evidence: `validation/evidence/web-firefox/`, verdict `web-firefox-10-windows-2000-x86-legacy.json`, procedure `validation/procedures/web.md`.
- The spec Clarifications of 2026-11-15 (PoC validation scope): success on the lowest testable system stands for newer ones, other rows stay `not_tested`. The owner decided the same day that Internet Explorer up to 9 is dropped for the PoC and that the Web Legacy path is validated on the lowest testable browser only.

## Decision

1. **Two paths, one source** (C++11 backend, `bridge/wasm/exports.txt` = the six `loomora_*` functions, `-fexceptions` because the backend throws and catches at the C boundary):
   - **WebAssembly path**: the **current Emscripten, 7.0.0** (emsdk checkout `708dcbc`, `7.0.0-1-g708dcbc`; node 24.19.0 of that emsdk), `cmake/toolchains/emscripten-wasm.cmake` (`-sWASM=1`), output `loomora-wasm.js` + `loomora.wasm`. Used by the Modern UI and by every Legacy browser that has WebAssembly.
   - **JavaScript path**: **Emscripten 1.39.20 fastcomp** (`emcc` 1.39.20, commit `45d43807ec2b74673acc703dd1145ac0d2d1040a`, clang 6.0.1), `cmake/toolchains/emscripten-js-fastcomp.cmake` (includes `emscripten-js.cmake`: `-sWASM=0 -sLEGACY_VM_SUPPORT=1 -fexceptions -O2 -sALLOW_MEMORY_GROWTH=1 -sMODULARIZE=1 -sENVIRONMENT=web,worker,node`, plus `--memory-init-file 0`), preset `web-js-fastcomp`, output `loomora.js` (the memory image inside, no `.mem`). It is the toolchain R8 named as the fallback, and the one run on Firefox 10.
2. **Pinned build tools** (what `tools/build.py web legacy` uses; each lives in `$HOME` of the WSL build machine, never in the repository):
   - the current emsdk at `~/emsdk` (`LOOMORA_EMSDK`), activated by `emsdk_env.sh`;
   - the fastcomp emsdk at `~/emsdk-fastcomp` (`LOOMORA_EMSDK_FASTCOMP`): a clone of emsdk **checked out at tag 3.1.29** (commit `0b2084f`), because the current emsdk refuses fastcomp; its own **node 14.18.2** (`NODE_JS` of its `.emscripten`), activated through `EM_CONFIG` and the `PATH`, not through `emsdk_env.sh`;
   - **acorn 7.3.1**, the copy inside the fastcomp emsdk (`fastcomp/emscripten/node_modules/acorn`), run by `tools/trials/web-node/es-level.js` under `node` of the host (v26.13.1 when run) to check at build time that `app.js` and `loomora.js` parse as `ecmaVersion 3` (the build fails otherwise). `loomora-wasm.js` is not checked: it is modern on purpose and this acorn does not finish on it. The reading of the Emscripten 7.0.0 output (`ecmaVersion 2021`) used acorn 8.19.0 of the current emsdk.
3. **Loader rule** (`ui/legacy/web/app.js`, ECMAScript 3, `var` / `function` only): if `typeof WebAssembly === "object"`, load `loomora-wasm.js` and `loomora.wasm`; otherwise load `loomora.js`. A browser that has WebAssembly never takes the JavaScript build, so the older and slower path is not applied to everyone (ADR 0004). A query `path=js` forces the JavaScript path (tests, node harness). The choice is a run-time check, declared as fallbacks `web-js-instead-of-wasm` and `web-es3-glue` in `validation/fallbacks.json`.
4. **Internet Explorer 6 to 9 are dropped** from the Web target. The Web Legacy floor is a browser with typed arrays and no WebAssembly: Firefox 4, Chrome 7, Internet Explorer 10 and later have typed arrays natively. Only Firefox 10.0 was run; under the PoC rule it stands for newer browsers.
5. The ES3 syntax rule on `app.js` and on the generated glue is kept even though Firefox 10 accepts ES5 syntax: it costs nothing and keeps the page loadable by any engine that has typed arrays.

## Rejected alternatives

- **Current Emscripten for the JavaScript path** (`-sWASM=0 -sLEGACY_VM_SUPPORT=1`): the flags are accepted but the output is ECMAScript 2021, a syntax error before any code runs on a Firefox 10 (reading of the syntax, no run). A transpiler (down to ES3) over it was not tried. The option is also "deprecated, under consideration for removal" in 7.0.0.
- **Emscripten 1.39.20 with the upstream backend** (`-sWASM=0`, wasm2js): works under node with an ES3 glue, but it writes a separate `.mem` file by default and was not run in a browser. Kept in reserve, not chosen: fastcomp is what R8 named and what Firefox 10 ran.
- **Emscripten 1.29.12 plain arrays** (for IE 6 to 9): compiler crash on the 64-bit arithmetic of libc++ (measured); the glue still needs ES5 library functions; it needs Python 2.7, clang 3.3 and local patches. Later releases cannot produce plain arrays (source of 1.30.5).
- **A C-only backend without libc++ and without 64-bit integers** (to compile with 1.29.12): not tried, and it contradicts ADR 0001 (strict C++11 backend behind a C API); `loomora_probe_record` also takes an `int64`.
- **A second implementation of the core in plain JavaScript** for IE 6 to 9: it would duplicate the logic that the project keeps in one place (one backend, UIs with no logic) and could not be shown to behave like the backend except by running the same vectors twice.
- **A typed-array polyfill for IE 9, or a post-processor that rewrites the asm.js heap accesses into function calls**: not tried. IE 6 to 8 cannot index an object that is not an array, and the views of one buffer would have to alias; a post-processor is a compiler stage of our own to write and maintain, with no browser to prove it.
- **WebAssembly only**: drops every browser without it, Firefox 10 included, against the Legacy floor.

## Consequences

- **Verified**: both paths build from the same source (`python tools/build.py web legacy`, ctest under node for each), 15 of 15 reference vectors through the page under node for each path, and the JavaScript path in Firefox 10.0 on Windows 2000 (14 of 15, the difference being a property of the text field).
- **Not verified, not claimed**: the WebAssembly path on any old browser (a current headless Chrome was a smoke test only, and it does not start on `file://`); Firefox 4 to 9 and 11 and later, Chrome 15, Safari 5.1, Opera 11.5, Internet Explorer 10 and 11; Windows 2000 SP4; real hardware; memory figures (Firefox 10 has no `performance.memory`); the upstream 1.39.20 build in a browser; the speed or even the feasibility of any IE 9 typed-array emulation.
- Fastcomp is deprecated (`emcc` says so, and that `ALLOW_MEMORY_GROWTH` disables some asm.js optimisations). The JavaScript path depends on an old emsdk, an old node and a download of their binaries by `emsdk`; no copy is kept in the repository, so the toolchain can become hard to reproduce. The versions above are pinned to make that visible; the cost is two emsdk installations on the build machine.
- Facts the Web UI handles because of this choice: `-fexceptions` is mandatory (with Emscripten's default a throw aborts the module); `loomora_probe_record` returns `rss_kb` (int64) as a BigInt in the WebAssembly build and as two 32-bit numbers in the JavaScript one; list settings of 1.39.20 accept only JSON arrays, so `exports.txt` and `runtime-methods.txt` are JSON arrays; the glue needs `Function.prototype.bind`.
- Research R8 (still names IE 9 and says "first with the current Emscripten"), tasks T070 and T086 and the first wording of S5 describe the earlier plan; this record supersedes it. `validation/spikes.json` S5 points to this record.
- The Modern UI (TypeScript, WebAssembly only) is unaffected.
